# 软件内侧栏与多会话

本节是 CADCraft 已实现架构的可迁移设计，不是把固定补丁粘贴到任何软件。UI 框架、语言、事件模型及文档生命周期适配目标软件。

## 先选择运行时

先读 [agent 适配](agent-adapters.md) 的运行时契约。以下协议步骤仅针对已实现的 **Codex app-server**；Claude Code、Cursor 或其他后端需要独立适配，不能替换可执行文件后照搬 JSON-RPC。制作 agent 可以任意选择，内嵌运行时不因此自动改变。共有的 UI、文档身份和会话约束仍适用。

## Codex 参考运行时

外部 agent 走 MCP。软件内侧栏在本次实现中使用本机 Codex app-server 的 stdio JSON-RPC，并直接回调软件的同一组文档命令。动态工具不是 MCP server；除非明确需要，不把回调又绕回外部 agent。

先核对当前 `codex app-server --help`。需要具体字段时使用当前版本生成的 schema，而不是照搬历史例子：

```bash
codex app-server generate-json-schema --help
```

协议顺序来自本机已运行的实现：

1. 启动 `codex app-server --listen stdio://`，后台读写 JSON 行。请求用独立 ID，区分响应、通知、服务器工具请求；设超时和消息长度上限。
2. `initialize` → 收到响应 → `initialized` 通知。当前动态工具目录需要实验能力时按 schema 声明，不能默认未来版本始终需要同一开关。
3. `config/read` 读取默认模型设置；`model/list` 分页加载可选模型及其思考强度、图片能力。拒绝重复游标，限制页数。
4. `thread/start` 创建会话，附加目标软件说明和动态工具 schema。namespace、字段及返回形状以当前版本为准。
5. 每次 `turn/start` 携带当前文档快照、用户请求、可选文档视图，以及当前选定的模型和思考强度。覆写可能在 thread 内保持；“恢复默认”也要显式用解析出的默认值覆盖。
6. 消费 `item/agentMessage/delta`、最终消息与 `turn/completed`。处理 `item/tool/call` 时先检查目标身份和取消状态，再在软件线程调用命令并回传结构化结果。
7. 停止时发送 `turn/interrupt`，先让本地工具守卫失效；没有 turn ID 的待连接请求也必须取消。掉线、初始化失败和不支持的交互要产生可理解的错误，不让 UI 一直显示忙碌。

本次 CADCraft 在 app-server 子进程中局部停用自己的外部 CADCraft 插件，避免同一模型通过另一条工具链修改不同窗口。迁移时根据实际重复入口处理，只影响该子进程，不改全局插件状态。不要复制案例中的 `approvalPolicy=never` 或权限设置到新环境；沿用目标环境已授权策略。

复用用户本机 Codex 登录，不复制账号文件到 skill。不同 provider 是否支持图片/动态工具须用真实返回和测试确认。启动器只继承必要环境，网络代理有需求时局部配置，回环软件控制通道应在 NO_PROXY 内，不随意改系统全局代理。

## UI 的必需行为

- 始终可见的启动状态和启动按钮；首次发送也可自动连接。
- 运行时能枚举时，模型与思考强度来自服务目录，不写死旧型号；不支持的设置不展示为可用。验证合法组合，连接中/回复中防止无效切换，发送下一条时应用设置。
- 明确显示当前文件名称、单位/状态、是否附带视图。只读取该软件文档，不能宣称读取全桌面。
- 输入框支持目标 Linux 输入法；先识别 Fcitx/IBus，再配置进程环境。CADCraft 的 Fcitx5 是这台主机的选择，不是所有机器的默认。egui 使用能显示中文的字体，并检查焦点与 IME composition。
- 收起后保留可见的重开按钮；快捷键即使输入框有焦点也能重开。隐藏面板不等于停止/清空对话。
- 每次发送获取最新快照；实时监听需求另加事件订阅与节流，不默认不断发送模型请求。
- 遇到软件缺少的能力，如真正三维实体，明确支持范围。接外部后端时返回生成文件和验证结果，而不是把截图/线框当成实体。

## 文档和会话状态

概念状态（字段名按目标项目调整）：

```text
DocumentUID → DocumentConversations
DocumentConversations = { activeConversationId, conversations }
Conversation = {
  conversationId, threadId?, runtime?, messages, draft,
  modelSelection, includeView, lastArtifact,
  targetDocumentUID?, turnId?, requestGeneration, cancelled
}
```

- 新文档生成稳定 UID，自动分配一段空白会话；继承用户默认模型/强度即可，不带入别的文档消息。
- 新对话分配新 conversation ID，旧会话完整留在列表。列表显示编号和首条用户消息摘要；空白对话有清晰名称。ID 不应因为排序/筛选而改变。
- 切换会话恢复消息、草稿、设置、最近输出和仍可用的 thread；切换文件恢复那个文件自己的列表和上次所选会话。
- 关闭一个较早的文件标签不能导致后面文件聊天串位。覆盖 UI 菜单、控制命令、命令行、直接引擎切换等入口。
- 不仅 UI 操作需要守卫：后台工具请求和建模任务完成也需要检查请求归属。

推荐每次请求捕获 `(documentUID, conversationId, generation, turnId)`。真正执行前及异步完成时检查仍属于相应请求、未取消，并按软件线程模型执行。切换时取消旧工作并使旧 generation 失效；不要把旧请求的目标 UID 更新成当前文件。

迟到结果可以留在旧会话中，但不能修改新文档、自动打开新窗口或重新进入回复状态。保留独立 runtime 时要限制资源；也可在不活跃时释放连接、保存记录并重连，但不能把历史展示成仍在运行的服务 thread。

## 持久化和迁移

打开期间以文档 UID 管理；跨重启通过规范化绝对文件路径/软件原生文档 ID 匹配。新建未保存文件没有可恢复的稳定路径，不能把上次空白文件的聊天注入新文件。若要求恢复未保存文件，另建明确的恢复项目/快照机制。

持久化保存每个文件的会话列表、active ID、消息、草稿、模型设置及产物路径。不要持久化为真：busy、待工具请求、进程 PID、连接中的状态。恢复时 thread 未必有效；本次实现恢复本地消息并在新 thread 附带有界历史上下文，不声称恢复完整服务端会话。

旧版本只有一段会话时迁移成会话 1。另存为保留当前会话，同时为旧、新路径分别保存当时的历史；明确同路径打开多个副本/重命名的策略，不能无意覆盖另一份状态。

本机采用每文件最多 64 段会话，每段最近 100 条消息，最多 64 个已保存文件、8 MiB 总记录。它是有界近期历史而非无限归档。迁移产品应据用户需求选限额、给出提示或外部归档；不自动删除会话来实现“新对话”。
